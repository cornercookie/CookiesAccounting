## 功能描述

分錄記錄預設標記為「待確認」，其他成員可點「我確認這筆是我花的」或「這筆不是我花的」，記錄確認者與時間，避免共同帳本中「這筆是誰花的？」爭議。

## 專案函數與術語說明

- 輸出轉義函數（h()）：用於防護跨站腳本（XSS）。
- 跨站請求偽造（CSRF）：防護網頁請求被偽造的機制。
- PHP 資料物件（PDO）：用於資料庫查詢的預備陳述式介面，選用理由為符合專案「純 PHP + PDO 預備陳述式」技術約束，防止 SQL 注入。
- 登入保護機制（requireLogin()）：檢查 $_SESSION['user_id']，未登入導向登入頁。
- 帳本存取權限表（ledger_access）：記錄使用者對各帳本的角色（擁有者（owner）/成員（member）/檢視者（viewer））。
- 稽查記錄表（audit_log）：記錄誰在何時做了什麼操作，僅新增不刪除。
- 預寫日誌（WAL）：SQLite 資料庫日誌模式，支援多讀寫併發，選用理由為 SQLite 在多併發讀寫場景下可避免鎖定失敗，符合共享主機環境需求。
- 狀態標籤（chip）：分錄列表中顯示確認狀態的 UI 組件，包含待確認、已確認、有爭議三種狀態。

## 使用者故事

作為家庭成員，我想確認或認領我花過的記帳記錄，避免家人誤以為是我花的錢。

## 預期行為

1. entries 資料表新增欄位：確認狀態（ack_status，pending/confirmed/disputed，預設 pending）、確認者 id（ack_user_id）、確認時間（ack_at）。
2. 分錄列表每行顯示狀態標籤（chip，狀態標籤 UI 組件，顯示待確認/已確認/有爭議）。
3. member/擁有者可對該筆記錄執行確認或爭議動作（POST 表單，含 CSRF 權杖）。
4. 確認後更新 ack_status、ack_user_id（目前登入使用者）、ack_at（SQLite datetime('now','localtime')）。
5. 稽查記錄表（audit_log）記錄動作，action 為 entry_confirm 或 entry_dispute。
6. 僅記錄建立者本人或帳本擁有者/管理員可變更確認狀態（避免他人亂改）。
7. 所有輸出經 h() 轉義。
8. SQL 查詢使用 PDO 預備陳述式，具名佔位符。
9. 權限檢查：使用者對該帳本有 ledger_access，且符合操作條件。

## 資料流（Data Flow）

使用者於分錄列表點擊「確認」或「爭議」按鈕，以 POST 提交含 CSRF 權杖的表單；伺服端驗證登入階段（requireLogin）與帳本存取權限（ledger_access）；檢查使用者是否為記錄建立者本人或帳本擁有者/管理員；以 PDO 預備陳述式 UPDATE entries 設定 ack_status、ack_user_id、ack_at；寫入 audit_log 記錄動作；所有輸出經 h() 轉義。

```mermaid
flowchart TD
    A[使用者點擊確認或爭議] --> B[POST 表單含 CSRF 權杖]
    B --> C[requireLogin 驗證登入]
    C --> D[ledger_access 權限檢查]
    D --> E[檢查是否為記錄建立者或擁有者/管理員]
    E --> F[PDO UPDATE entries 設定 ack_status/ack_user_id/ack_at]
    F --> G[audit_log 記錄 entry_confirm/entry_dispute]
    G --> H[分頁重新載入顯示狀態標籤 h() 轉義]
```

## 業務驗收條件

- 分錄列表每行顯示確認狀態標籤（待確認/已確認/有爭議）。
- 確認或爭議動作僅允許記錄建立者本人或帳本擁有者/管理員執行。
- 確認/爭議表單提交時，系統驗證跨站請求偽造（CSRF）權杖，驗證失敗拒絕請求。
- 操作成功後，確認狀態、確認者與確認時間寫入記錄，稽查記錄表記錄對應動作。
- 所有使用者可控輸出經輸出轉義函數（h()）轉義。

## 介面契約（entry_ack.php）

- 請求方法：POST
- 端點路徑：./entry_ack.php（或整合至 ./ledger.php）
- 請求欄位：
  - entry_id：記錄編號，整數，業務意義為欲確認或爭議的分錄記錄 id。
  - action：動作類型，值為 confirm（確認）或 dispute（爭議），業務意義為使用者對該筆記錄的確認意圖。
  - csrf_token：跨站請求偽造（CSRF）權杖，字串，以 hash_equals() 驗證。
- 回應格式：HTTP 重導向至分錄列表頁面，或 JSON 回應（視實作而定）。
- HTTP 狀態碼：200（成功）、400（參數錯誤）、403（權限不足）、500（伺服器錯誤）。
- 錯誤行為：CSRF 權杖驗證失敗回 403，權限不足回 403，資料庫寫入失敗顯示通用錯誤頁並記錄至 private_data/error.log。

## 錯誤處理與邊界條件

- CSRF 權杖驗證失敗：拒絕請求，顯示通用錯誤訊息。
- 權限不足：顯示「您沒有權限變更此記錄的確認狀態」，HTTP 回應 403。
- 重複確認：同一記錄可多次變更狀態，每次都寫入 audit_log，不阻止重複操作。
- 資料庫寫入失敗：顯示通用錯誤頁，詳細錯誤寫入 private_data/error.log。
- 記錄不存在或已軟刪除：顯示「找不到該記錄」。

## 身分驗證與權限控管

- 身分驗證：依賴既有 session 登入機制，requireLogin() 檢查 $_SESSION['user_id']，未登入導向 login.php。
- 權限控管：使用帳本存取權限表 ledger_access，角色分為擁有者（owner）、成員（member）、檢視者（viewer），僅記錄建立者本人或帳本擁有者/管理員可變更確認狀態。
- 資料傳輸加密：依賴既有超文字傳輸協定安全版（HTTPS）Session Cookie 設定（secure、HttpOnly、SameSite=Lax）。

## 非本期範圍（Out of Scope）

- 確認通知：本期僅於網頁顯示狀態，不發送電子郵件或推播通知。
- 確認歷史紀錄：本期僅顯示目前狀態，不保留確認變更歷史。
- 批次確認：本期僅支援單筆確認，不支援一次選擇多筆記錄確認。

## 非功能性需求

- 預期效能：確認動作為單筆更新，回應時間在可接受範圍內，具體閾值待效能測試後確認。
- 併發處理量：單筆 UPDATE 操作，SQLite WAL 模式支援多併發寫入。
- 資料保留策略：ack_status 與 ack_at 隨 entries 記錄生命週期保留，不額外歸檔。
- 系統可用性：確認失敗時顯示錯誤訊息，不影響分錄列表檢視。
